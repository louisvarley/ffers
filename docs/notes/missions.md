Status (2026-10-25): the BBS's contract offers are accepted, tracked and
settled; the port has a journal page and a comms page; and the source's
completion/rank/medal text is expanded from its own `0xff`-coded strings. The
civilian passenger, parcel and removal/assassination offers generated by the
merged Bulletin Board (`F638`/`F643`) are reachable, and so is the military

Source: `jjffe-master/ffe.asm`/`ffedat.asm`; the port is

mission_offer`/`military_offers`/`clear_post`, `ffe_rs::station::{Screen::

## Contract fields and derived values

The contract is F290's five dwords:

```text
+0x00  reward           BBS row StrVars[0] (whole credits)
+0x04  basic_data       F638's `rand&7 | additive<<9 | package<<13`
+0x08  destination      StrVars[2], the `0x85ff` system code
+0x0c  deadline         F534: accept day + 0x1c; F632 military: +14..77
+0x10  name seed        StrVars[3] (F791's 0x92xx names)
```

`Mission` keeps those fields plus the source code, origin system/station name,
the passage/parcel text (`StrVars[1]`) or removal title (`StrVars[4]`), the
kind, and the status. The
reward is never recomputed: it is the BBS row's money slot, which the existing
`bulletin::ship_job`/`removal` generator already derived from
`DATA_006171..6174`/`DATA_006214`. The acceptance deadline is the source's
28-day rule; the removal ad's displayed date (`F643`'s `game day - 0x121cf7 +
7..70`) is not used as the contract deadline because F534 overwrites the
deadline slot when the contract is created.

Passenger/parcel encoding: `basic_data`'s low three bits are the passenger
count minus one, bit 13 marks the "small package" passage (0x991c, no cabins),
and bits 9..12 are the mission additive. `bulletin::ship_job` sets the fifth
`Var` to this word (it was previously always 0), so `missions::offer` can read
the count and the package flag without a second record. The port does not add
the FFED3D `ships` field (bits 16+), which is not in the DOS F638 word.

## Implemented actions

* **Accept** (`F534`): `State::accept` checks the 0x3b cap, appends the
  contract, writes the 0x992a page/journal entry and the comm message. On the
  reply page (`missions::Negotiation`) the negotiated money is the contract's
  reward (or half/all of it, with the advance paid into cash), the page is
  0x992a/0x992b/0x992c (`State::accept_page`) and a granted permit sets its
  `DATA_009091` bit. `main` removes the advertisement (`F535`), posts the page
  to the console log (`F349`, `Cue::Message`) and beeps the row click (`F361`).
* **Complete** (`F303`): `State::settle` pays the whole-credit reward (the
  caller adds `reward*10` to the tenths cash field), raises `reputation` by one
  (cap 5), writes 0x9c31 (one passenger), 0x9c32 (a group), 0x9c33 (military
  delivery) or 0x9c34 (parcel/removal). F303 itself has no deadline test; a
  direct settlement after the deadline keeps the port's 0x9c2c page, which the
  source uses from F300's removal/military list, and pays nothing. A
  failure/expiry writes 0x9c37 (F302), and the military-late 0x9c38 page.
* **Tick** (`F301`/`F302`): `State::tick(day, system)` runs F301 first: every
  passenger/parcel/military-delivery contract past its deadline gets the
  0x8000 mark and 0x9c36 if it is a passage (a package and a seed-0 military
  contract are marked silently). F302 then tests that mark before the current
  system, so an overdue contract fails wherever the player is: `-2`
  reputation, 0x9c37, and it leaves the active list. A seed-0 package
  delivered to its destination is the one exception (0x9c38, no pay, no
  step). Only a contract that is not overdue and due at `system` reaches
  `settle`. `main` runs this each frame against the navigator's current system
  (not only when docked), reproducing F302's arrival check. The removal and
  military-strike list is F300's (see "Missing data").
* **Abandon**: `State::abandon` writes the port's 0x9c37 page and loses one
  reputation step (F485's source page is 0x9943/0x9946 and its loss is `-8`).
* **Military package** (`F493`/`F623`/`F629-F632`/`F509`): selecting a
  recruitment ad opens `Screen::Military`. The list regenerates from a
  station/day stream; F629's 8 cargo variants are always offered, F630's 4 at
  more than 0x10 rank points and F631's 4 at more than 0x51. F632's decoded
  reward is `150/550/750 + 50*additive + 100*random(4)`, and its deadline is
  `day + 14 + random(0x40)`. Accepting uses F509's 0x2000/tier `basic_data`;
  completion uses F303's `seed==0` branch (0x9c33) and F306's rank page
  (song 7). A package delivery has no medal: F509's low bits are 0, so
  F303 picks `DATA_005115[0]`/`DATA_005116[0]` (0xff) and F307 is skipped.
  The offer taken today is filtered from the regenerated list (the source
  removes its `DATA_009004` slot).
* **Military briefing** (`F508`/`F495`/`F496`/`F506`; 2026-11-20): selecting
  a mission row no longer accepts it. F352 prints the offer's description on
  the console and F342/F523 replace the list with the suggested responses on
  F331's screen 1 (`Screen::Briefing`, `missions::Briefing`). The rows and
  their `DATA_005288` handlers are:

  | offer | rows | handler |

  | package 0x9854 (F508) | 0x9858..0x985f, 0x9860 | accept, the shared seven, return |
  | photograph 0x9855 (F495/F496) | 0x9858, 0x9866, 0x9865, 0x9859..0x985f, 0x9860 | accept, camera, destination, shared seven, return |
  | bombing 0x9856 (F496) | 0x9858, 0x9867, 0x9868, 0x9865, 0x9859..0x985f, 0x9860 | accept, missile answers, destination, shared seven, return |
  | assassination 0x9857 (F506) | 0x9861..0x9864, 0x9859..0x985f, 0x9860 | accept, how to find, ship, deadline, shared seven, return |
  | removal 0x981f..0x9822 (F460) | 0x9861..0x9864, 0x983e, 0x983f | accept, how to find, ship, deadline, two ways to hang up |

  `0x9858`/`0x9861` accept (F509/F498/F467), `0x985a` shows the description

* **Journal**: the source's `MISSION.DAT` journal archive is not in the cache;
  the port's journal records the contract events it can generate (accept,
  complete, fail/expire, abandon, military rank) with the source page text.
* **Comms**: `State::pages` holds the pages; the comms screen lists them newest
  first and `ReadPage` plays the page's source song (7 for F306's rank page, 10
  for F307's medal page) and marks it read.

## Journal and comms screens

`station::Screen::Journal` and `Screen::Comms` are port pages, not extra
station services (the original journal is the ship library's viewer F76/F78/F81
and the comms list is F343's). They use the 33-pixel paragraph layout, wrap at
312 pixels, have no row button and show the Go Back arrow (F566). `J` and `C`
open them while the station board has focus; they are called out as port
conveniences in the report. The status/cargo line is omitted on these pages so
the text has the full panel. The title for the journal is the source's
`SHIP LIBRARY ARCHIVES` (DATA_002304); the comms page is `Communications`.
`Screen::Military` is the 0x9827/0x9828 recruitment ads' target: the BBS
33-pixel layout with its row button, command text at x 140, and Go Back to the
bulletin board (F493's "Return to Mission List" is 0x9860). The list is the
menu F493 builds: the station's offers first, then the scripts' F346 rows from
signal 3 (mission 23's `0xa9b9`, which starts mission 25), in the menu's order.

## Persistence

`Flight::missions` is a `#[serde(default)] ffe_core::missions::State`, so a
save from before this slice loads with no contracts, journal or pages. The
state validates its bounds in `Flight::validate` (the 0x3b acceptance cap,
256 journal entries, 64 pages, reputation -0x80..5, rank 0..8, string lengths).
`Mission::overdue_noticed` is a serde-defaulted F301 flag, so an old save's
contracts simply get noticed on the next tick.

   terms pay everything now. The source details reproduced as-is:

   * F528's permit systems are F529's three codes (0x0aa4b718, 0x16a49718,
     0x0aa4971a) with `DATA_009091` bits 14, 13 and 15 — the port ORs them
     into `npc::Career::medals`, whose 13..15 are the three permit names.
   * F531/F532's refusal roll is F921, a deterministic scramble of the entry's
     `basic_data` and seed that **mutates both words**; the port's
     `missions::f921` runs the same steps, so a low-reputation advance demand
     changes the words the contract is built from exactly as the original.
   * F531/F532 both refuse once bit 0x80 is set, so 0x40 can only be reached
     before it; F534 pays the all-now terms only when both bits are set. The
     port keeps that behaviour (the test notes it).
   * F534's acceptance page is 0x992a, or 0x992b/0x992c for the half/all-now
     terms (`State::accept_page` takes the page F534 wrote).

   **F460's removal conversation is ported (2026-11-20).** A removal ad opens
   the 0x99c4 page and the 0x9861..0x9864/0x983e/0x983f rows (see "Military
   briefing" above). Two approximations remain: F467 writes the source's
   0x34-byte removal contract into the 52-byte military list and refuses at
   six entries, while the port records F290's 20-byte contract and caps at
   `MAX_MISSIONS` (0x3b); and the in-system target F291 places is still the
   trader leaving the place nearest the player, not F466's destination
   starport from the conversation. The contract still records the passenger
   count.
4. **Rank.** `military_points`/`rank` use `DATA_005114`'s thresholds. The
   nine names are the first nine Federal rank strings from `DATA_005104`'s
   0x9c4e..0x9c56 (Private..Captain); the Imperial ladder (0x9c5b..0x9c66) is
   not selected because the 20-byte contract has no allegiance field. The
   +500 points per delivery is the port's documented choice, not a source
   constant (F300's `pointGain` table is for the 52-byte military contracts).
   F306's promotion/demotion page is therefore always the current rank, not a
   before/after comparison.
5. **Journal archive.** `MISSION.DAT`'s offset/bit-permutation archive is
   imported (`base:text/journal`, `ffe_core::journal`), the scheduler is
   ported (`journal_library`) and the ship-library viewer draws an issue
   (`ffe_rs::journal_page`); see `docs/notes/journal.md`. The station's own
   `Screen::Journal` still lists the contract events this module records,
   which is a port page; the original journal is the ship library's.
6. **Money unit.** The source's `DATA_008888` is in tenths; the port's
   `Flight::credits` is the same unit (`$100.0` is 1000). `missions::settle`
   returns whole credits and `main` multiplies by ten; the scripted test checks
   the conversion. If a future cash model changes the unit, this is the one
   conversion to update.
7. **Sound.** Accept/complete use F349/F351's `0x16` bong (`Cue::Message`);
   the row click is F361's `0x14` beep. Military package completion calls
   F306's song 7. F307's song 10 is wired for the medal-bearing military
   constructors, which are not ported (a package delivery's medal code is
   `0xff`, so F307 is skipped). No new sample or song asset is needed.
8. **F300's removal list, F304/F305 and F485.** The overdue pass above is
   F301/F302's passenger list (F290's 0x14-byte records). F300's separate
   0x34-byte removal/military-strike list has its own deadline page (0x9c29)
   and is still the port's previous approximation: `tick` expires an overdue
   removal with 0x9c29 and one reputation step. F302's late-package branch
   posts 0x9c38 and removes the contract, but the source also calls F304/F305
   and F306's rank page there; the port does not draw that page (its text is
   the promotion/current-rank page, which would be wrong for a late arrival).
   F485's abandon page and `-8` step (`0x9943`/`0x9946`) are still the port's
   0x9c37 page and single-step loss.
